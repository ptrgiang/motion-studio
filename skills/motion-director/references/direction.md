# Direction decisions

## Build a useful brief
Write a viewer question and a visual answer. For a product film, prefer a visible interaction to a feature adjective. For a data story, identify the comparison, units, period, source and what inference is supported. For typography, define the words' rhythm and hierarchy. Do not force the same hook-problem-reveal-CTA structure onto every film.

## Translate reference into rules
Record specific observable traits: muted warm background, condensed uppercase headline, left-edge grid, hard cuts after long holds. Avoid terms that cannot be checked, such as "premium", without concrete examples. Extract start, midpoint, peak and end frames from reference footage. Estimate timing from several transitions, not one screenshot. Distinguish camera movement, object motion and editing.

## Asset integrity
Capture a real app only through authorized tools/accounts; keep credentials and private customer data out of the footage. Prefer supplied captures when available. Preserve legibility and actual state progression. A rebuilt vector overlay may highlight real UI; it must not silently change the underlying screen or imply nonexistent features. If a screenshot cannot show an interaction honestly, use supplied footage or request the missing state.

## Failure example
Request: "16s accounting-app launch, real UI only", supplied asset: logo. Output: usable concept and required SCREEN-01/02/03 inventory, blocked production proof. Do not draw an invented balance dashboard. Request: "abstract poem", no product assets: create original shapes and typography without treating real UI as required.
